# E-Commerce Data Lakehouse
# Source Data Dictionary


## 1. Overview

### 1.1 Purpose

This data dictionary defines the structure, meaning, constraints, and
expected values of the source data used in the End-to-End E-Commerce
Data Engineering Platform.

The purpose of this document is to provide a consistent reference for
the source-system entities and their attributes before data generation,
ingestion, transformation, and analytical modeling.

The data dictionary will serve as a foundation for:

- Designing the source data model
- Building the Python source-data generator
- Defining primary and foreign key relationships
- Defining data types and allowed values
- Designing data-quality scenarios
- Building the ingestion pipelines
- Transforming data through the Medallion architecture
- Designing the Kimball warehouse and Inmon EDW
- Supporting the analytical requirements of the Power BI dashboards

The source data is intentionally designed to represent realistic
e-commerce data, including data-quality issues that will later be
identified and handled by the data pipeline.

---

### 1.2 Scope

This data dictionary covers the source-system entities used by the
e-commerce platform.

The business scenario represents an international e-commerce company
that sells products to customers across multiple countries.

The source environment contains data generated by multiple business
systems, including:

- Customer System
- Product Catalog
- Order System
- Payment System
- Shipping System
- Review System
- Marketing System
- External APIs

The core source entities covered by this dictionary are:

1. Customer
2. Product
3. Order
4. Order Item
5. Payment
6. Shipping
7. Review
8. Marketing Event

External API data, such as exchange-rate data, will be documented
separately because it does not follow the same entity structure as the
core transactional source systems.

This document focuses on the source layer. It does not define the
final Gold-layer models, Kimball dimensional model, Inmon Enterprise
Data Warehouse, or Power BI semantic model.

Those models will be derived from the source data during later phases
of the project.

---

### 1.3 Naming Conventions

The source data model uses a consistent naming convention to make the
data easier to work with across Python, SQL, PostgreSQL, dbt, and the
analytical layers.

#### Table / Entity Names

Entity and table names use `snake_case` and are written in lowercase.

Examples:

- `customer`
- `product`
- `order`
- `order_item`
- `payment`
- `shipping`
- `review`
- `marketing_event`

#### Column Names

Column names use lowercase `snake_case`.

Examples:

- `customer_id`
- `first_name`
- `registration_date`
- `order_date`
- `shipping_country`


# 2. Source Entities

## 2.1 Customer

### Description

The `Customer` entity stores information about customers registered in the
e-commerce system. It is used to analyze customer demographics, customer
registration, customer activity, and customer behavior.

### Attributes

| Column | Data Type | Key | Nullable | Allowed Values / Format | Description | Generator Notes |
|---|---|---|---|---|---|---|
| `customer_id` | INTEGER | PK | No | Positive integer | Unique identifier for each customer | Generate unique sequential or random IDs |
| `first_name` | VARCHAR(50) | — | No | Alphabetic text | Customer's first name | Generate realistic names |
| `last_name` | VARCHAR(50) | — | No | Alphabetic text | Customer's last name | Generate realistic surnames |
| `email` | VARCHAR(255) | — | No | Valid email format | Customer's email address | Generate mostly valid emails; some malformed values can be introduced later |
| `phone` | VARCHAR(20) | — | Yes | International/local phone format | Customer's phone number | Generate valid phone numbers; some NULL values can be introduced |
| `gender` | VARCHAR(20) | — | Yes | Male, Female, Other, Unknown | Customer's gender | Generate values from the defined domain |
| `date_of_birth` | DATE | — | Yes | YYYY-MM-DD | Customer's date of birth | Generate realistic dates corresponding to adult customers |
| `country` | VARCHAR(100) | — | No | Country name | Country where the customer is located | Generate from predefined country list; inconsistent country names may be introduced later |
| `city` | VARCHAR(100) | — | No | City name | City where the customer is located | Generate cities consistent with countries |
| `registration_date` | DATE | — | No | YYYY-MM-DD | Date when the customer registered | Must not be later than the current source-data generation date |
| `customer_status` | VARCHAR(20) | — | No | Active, Inactive, Suspended | Current status of the customer | Generate values according to defined probability distribution |

### Primary Key

`customer_id` is the primary key of the `Customer` entity.

It uniquely identifies each customer and is referenced by other source
entities that contain customer-related information.

### Customer Relationships

The `Customer` entity participates in the following relationships:

- `Customer 1 : N Order`
  - `Order.customer_id` references `Customer.customer_id`.
  - One customer can place many orders.
  - Each order belongs to one customer.

- `Customer 1 : N Review`
  - `Review.customer_id` references `Customer.customer_id`.
  - One customer can write many reviews.
  - Each review belongs to one customer.

- `Customer 1 : N Marketing Event`
  - `Marketing_Event.customer_id` references `Customer.customer_id`.
  - One customer can generate many marketing events.
  - Each marketing event belongs to one customer.

### Customer Business Rules

1. `customer_id` must be unique and cannot be NULL.
2. `first_name` and `last_name` must be provided for every customer.
3. `email` must be provided for every customer.
4. Each customer should have a unique email address in the clean source
   model.
5. `registration_date` must represent a valid customer registration date.
6. `registration_date` cannot be later than the source-data generation date.
7. `date_of_birth`, when provided, must be earlier than `registration_date`.
8. `customer_status` must belong to the defined status domain:
   `Active`, `Inactive`, or `Suspended`.
9. A customer can have zero or many orders.
10. A customer can have zero or many reviews.
11. A customer can have zero or many marketing events.
12. The source data generator may intentionally introduce data-quality
    issues such as NULL values, malformed email addresses, inconsistent
    country names, and duplicate records. These issues represent the
    unclean source data that will be handled in later pipeline stages.

## 2.2 Product

### Description

The `Product` entity stores information about the products available in the
e-commerce catalog. It is used to analyze product performance, sales,
revenue, profitability, inventory levels, and category performance.

### Attributes

| Column | Data Type | Key | Nullable | Allowed Values / Format | Description | Generator Notes |
|---|---|---|---|---|---|---|
| `product_id` | INTEGER | PK | No | Positive integer | Unique identifier for each product | Generate unique sequential or random IDs |
| `product_name` | VARCHAR(150) | — | No | Product name | Name of the product | Generate realistic product names |
| `category` | VARCHAR(100) | — | No | Predefined product categories | Main category to which the product belongs | Generate from a predefined category list |
| `subcategory` | VARCHAR(100) | — | Yes | Valid subcategory | More specific classification of the product | Generate subcategories consistent with the selected category |
| `brand` | VARCHAR(100) | — | Yes | Brand name | Brand associated with the product | Generate from a predefined brand list |
| `supplier` | VARCHAR(100) | — | Yes | Supplier name | Supplier responsible for providing the product | Generate from a predefined supplier list |
| `cost` | DECIMAL(10,2) | — | No | Positive monetary value | Cost paid by the company to acquire or produce the product | Generate values lower than the selling price |
| `price` | DECIMAL(10,2) | — | No | Positive monetary value | Current selling price of the product | Generate realistic prices based on category |
| `stock_quantity` | INTEGER | — | No | Non-negative integer | Current quantity of the product available in inventory | Generate realistic inventory quantities; zero represents out-of-stock |
| `product_status` | VARCHAR(20) | — | No | Active, Inactive, Discontinued | Current status of the product in the catalog | Generate values according to a defined probability distribution |
| `launch_date` | DATE | — | No | YYYY-MM-DD | Date when the product was introduced to the catalog | Generate dates before or equal to the source-data generation date |

### Primary Key

`product_id` is the primary key of the `Product` entity.

It uniquely identifies each product in the product catalog and is
referenced by the `Order_Item` and `Review` entities.

### Product Relationships

The `Product` entity participates in the following relationships:

- `Product 1 : N Order Item`
  - `Order_Item.product_id` references `Product.product_id`.
  - One product can appear in many order items.
  - Each order item refers to one product.

- `Product 1 : N Review`
  - `Review.product_id` references `Product.product_id`.
  - One product can have many reviews.
  - Each review belongs to one product.

Therefore:

```text
     Product 1 ─── N Order_Item
     Product 1 ─── N Review
```

## 2.4 Order Item

### Description

The `Order_Item` entity represents an individual product included in a
customer order. It connects the `Order` and `Product` entities and stores
the quantity, selling price, discount, and historical product cost
associated with each item in an order.

`Order_Item` acts as the associative entity that resolves the many-to-many
relationship between orders and products.

### Attributes

| Column | Data Type | Key | Nullable | Allowed Values / Format | Description | Generator Notes |
|---|---|---|---|---|---|---|
| `order_id` | INTEGER | PK, FK | No | Existing `order_id` | Identifier of the order containing the product | Select from existing order IDs; invalid foreign keys may be introduced later |
| `product_id` | INTEGER | PK, FK | No | Existing `product_id` | Identifier of the product included in the order | Select from existing product IDs; invalid foreign keys may be introduced later |
| `quantity` | INTEGER | — | No | Positive integer | Number of units of the product included in the order | Generate realistic quantities, primarily between 1 and 10 |
| `unit_price` | DECIMAL(10,2) | — | No | Positive monetary value | Selling price of one unit at the time of the order | Generate based on the product price; historical prices may differ from current product price |
| `discount` | DECIMAL(5,2) | — | Yes | 0.00–100.00 (%) | Percentage discount applied to the item | Generate mostly zero or low discounts; occasional higher discounts may be introduced |
| `cost_at_sale` | DECIMAL(10,2) | — | No | Non-negative monetary value | Product cost at the time the item was sold | Generate based on the historical product cost |

### Primary Key

`Order_Item` uses a composite primary key consisting of:

```text
(order_id, product_id)
```

# 3. Cross-Entity Constraints

This section documents the primary keys, foreign keys, unique constraints,
and referential integrity rules that apply across the entities in the
e-commerce source system.

The constraints are based on the relationships defined in the finalized
Entity Relationship Diagram (ERD).

---

## 3.1 Primary Key Constraints

A primary key uniquely identifies each record within an entity.

The following primary keys are defined in the source system:

| Entity | Primary Key | Type | Description |
|---|---|---|---|
| `Customer` | `customer_id` | Single-column | Uniquely identifies each customer |
| `Product` | `product_id` | Single-column | Uniquely identifies each product |
| `Order` | `order_id` | Single-column | Uniquely identifies each order |
| `Order_Item` | `order_id`, `product_id` | Composite | Uniquely identifies a product within an order |
| `Payment` | `payment_id` | Single-column | Uniquely identifies each payment |
| `Shipping` | `shipment_id` | Single-column | Uniquely identifies each shipment |
| `Review` | `review_id` | Single-column | Uniquely identifies each review |
| `Marketing_Event` | `event_id` | Single-column | Uniquely identifies each marketing event |

### Primary Key Rules

1. Primary key values must not be NULL.
2. Primary key values must be unique within their entity.
3. `Order_Item` uses a composite primary key consisting of:
   `order_id` and `product_id`.
4. The combination `(order_id, product_id)` uniquely identifies an order
   item.
5. Primary key values should remain stable after a record is created.
6. The source data generator must primarily generate valid unique primary
   keys.
7. Duplicate primary keys may be intentionally introduced as data-quality
   problems to test the pipeline.

### Composite Primary Key — Order Item

The `Order_Item` entity does not require a separate `order_item_id`.

Instead, it uses:

```text
PK (order_id, product_id)
```
## 3.2 Foreign Key Constraints

Foreign keys establish relationships between the entities in the e-commerce
source system. A foreign key must reference an existing primary key in its
parent entity.

| Child Entity | Foreign Key | Parent Entity | Referenced Key | Relationship |
|---|---|---|---|---|
| `Order` | `customer_id` | `Customer` | `customer_id` | Customer 1 : N Order |
| `Order_Item` | `order_id` | `Order` | `order_id` | Order 1 : N Order Item |
| `Order_Item` | `product_id` | `Product` | `product_id` | Product 1 : N Order Item |
| `Payment` | `order_id` | `Order` | `order_id` | Order 1 : 1 Payment |
| `Shipping` | `order_id` | `Order` | `order_id` | Order 1 : 1 Shipping |
| `Review` | `customer_id` | `Customer` | `customer_id` | Customer 1 : N Review |
| `Review` | `product_id` | `Product` | `product_id` | Product 1 : N Review |
| `Marketing_Event` | `customer_id` | `Customer` | `customer_id` | Customer 1 : N Marketing Event |

### Foreign Key Rules

1. Every foreign key should reference an existing record in its parent
   entity.
2. Foreign keys must use a compatible data type with the referenced
   primary key.
3. Mandatory foreign keys must not contain NULL values.
4. Invalid foreign-key values may be intentionally introduced by the data
   generator to simulate source-system data-quality problems.
5. Invalid foreign keys must be detected during data-quality validation.
6. Invalid foreign-key records must not be included in trusted analytical
   datasets.
7. The original records should remain available in the Bronze/raw layer
   for traceability.

### Many-to-Many Relationships

The relationship between `Order` and `Product` is logically many-to-many.

It is resolved through the `Order_Item` entity:

```text
Order M ───── N Product
       │
       │
   Order_Item
```
## 3.3 Unique Constraints

Unique constraints prevent duplicate values or duplicate combinations of
values where uniqueness is required by the source-system business rules.

| Entity | Unique Constraint | Purpose |
|---|---|---|
| `Payment` | `order_id` | Ensures that an order has at most one payment |
| `Shipping` | `order_id` | Ensures that an order has at most one shipping record |
| `Review` | `(customer_id, product_id)` | Ensures that a customer can review a particular product at most once |

### Payment Unique Constraint

`Payment.order_id` is both a foreign key and a unique attribute.

```text
Payment.order_id
      FK + UQ
```
## 3.4 Referential Integrity Rules

Referential integrity ensures that relationships between parent and child
entities remain valid. A foreign key in a child entity must reference an
existing primary key in the corresponding parent entity.

The following referential integrity rules apply to the e-commerce source
system.

### Customer → Order

```text
Order.customer_id → Customer.customer_id
```

# 4. Data Quality Expectations

## 4.1 Missing Values

Missing values occur when an attribute contains `NULL`, an empty value, or
when the source system does not provide a value.

The source data is intentionally designed to contain missing values in order
to simulate realistic source-system data-quality problems.

### Expected Missing Values

Not every missing value is necessarily an error. Some attributes are
nullable by design.

Examples include:

| Entity | Attribute | Nullable | Example |
|---|---|---|---|
| `Customer` | `phone` | Yes | `NULL` |
| `Customer` | `gender` | Yes | `NULL` |
| `Customer` | `date_of_birth` | Yes | `NULL` |
| `Review` | `review_text` | Yes | `NULL` |
| `Shipping` | `delivery_date` | Yes | `NULL` |

For example, a `Shipping.delivery_date` of `NULL` can be valid when the order
has not yet been delivered.

### Missing Value Rules

1. Primary key attributes must never contain NULL values.
2. Mandatory foreign keys must not contain NULL values.
3. Attributes defined as nullable may contain NULL values.
4. The data generator should intentionally introduce some missing values
   in nullable attributes.
5. Missing values in mandatory attributes should be considered a data
   quality issue.
6. Missing values should be identified during data profiling and
   validation.
7. The pipeline should distinguish between legitimate NULL values and
   unexpected missing values.
8. Missing values should not automatically be replaced without a defined
   business rule.
9. The original missing value should be preserved in the Bronze layer.
10. Appropriate handling of missing values should occur during the
    Bronze-to-Silver transformation.

### Example

A valid record:

```text
customer_id | first_name | phone
------------|------------|--------
1001        | Omar       | NULL
```
## 4.2 Duplicate Records

Duplicate records occur when the same business record appears more than
once in the source data.

The source data is intentionally designed to contain duplicate records in
order to simulate realistic source-system data-quality problems and to
test the deduplication logic of the data pipeline.

### Duplicate Detection Keys

Duplicates should be detected using the primary key or the appropriate
business key for each entity.

| Entity | Duplicate Detection Key | Duplicate Rule |
|---|---|---|
| `Customer` | `customer_id` | Each customer ID must identify one customer |
| `Product` | `product_id` | Each product ID must identify one product |
| `Order` | `order_id` | Each order ID must identify one order |
| `Order_Item` | `(order_id, product_id)` | Each product can appear once within an order |
| `Payment` | `payment_id` / `order_id` | Each payment must be uniquely identifiable |
| `Shipping` | `shipment_id` / `order_id` | Each shipping record must be uniquely identifiable |
| `Review` | `review_id` / `(customer_id, product_id)` | A customer can review a product at most once |
| `Marketing_Event` | `event_id` | Each marketing event must be uniquely identifiable |

### Duplicate Record Rules

1. Primary key values must be unique within each entity.
2. The composite primary key `(order_id, product_id)` in `Order_Item` must be
   unique.
3. `Payment.order_id` must be unique because an order has at most one
   payment in the current source-system design.
4. `Shipping.order_id` must be unique because an order has at most one
   shipping record in the current source-system design.
5. `(customer_id, product_id)` must be unique in `Review`.
6. Duplicate records may be intentionally introduced by the data generator.
7. Duplicate records must be detected during data profiling and validation.
8. The Bronze layer should preserve the original duplicate records for
   traceability.
9. Duplicate records should be handled during the Bronze-to-Silver
   transformation.
10. The deduplication strategy must be documented and deterministic.
11. Records should not be deleted from the raw/Bronze layer simply because
    they are duplicates.
